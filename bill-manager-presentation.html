Strategic technology briefing

Trustworthy Bill Intelligence

How a deterministic bill calculator became a local, hybrid AI agent without giving the model control of financial truth.

Phi-4 Mini Qwen3 Embeddings SQLite BM25 Python

Two Minds AI Lab · Stage 0 → Hybrid Bill Manager

Open with the central design decision: this is not an attempt to make a model calculate bills. It is an attempt to let natural language safely reach trusted calculations and evidence. The project is small by design, so every failure can be seen, explained, and fixed.

The user problem

Five simple questions. Zero tolerance for invented answers.

What is due?

Find bills due in the next seven days and later this month.

How much?

Calculate upcoming and current-month totals exactly.

What changed?

Compare each bill and the overall month with prior history.

What is unusual?

Apply explicit percentage and absolute-change thresholds.

Which record?

Find the right bill from provider names, concepts, dates, or amounts.

Why trust it?

Show evidence and keep model variation away from financial facts.

The questions sound conversational, but they contain several different engineering problems: date windows, money arithmetic, anomaly rules, information retrieval, and natural-language intent. The solution separates these rather than asking one model to do everything.

The governing principle

Use AI for ambiguity.
Use code for accountability.

The model interprets the question. Python controls tools, validates matches, performs financial calculations, and formats the answer.

This is the most reusable lesson in the project. Models are valuable where the user is ambiguous: “power bill,” “home internet,” or “did anything jump?” They are not the right authority for arithmetic, identifiers, state transitions, or policy enforcement.

There is an agent loop, but it is not autonomous in the broad sense. All three tools are read-only. Phi-4 proposes intent; Python enforces tool coverage. Search identifies records, calculations enrich them, and bill_id is the join key. The final financial prose is rendered by code.

Division of labor

Each component contributes a different kind of intelligence.

Phi-4 Mini

Value: local language understanding and tool intent.

Not trusted for: money, dates, or final factual rewriting.

BM25

Value: exact providers, identifiers, and literal terms.

Strength: fast, explainable, no model required.

Qwen3

Value: concepts and synonyms such as “power bill.”

Strength: meaning beyond exact vocabulary.

Python

Value: policy, validation, calculation, joins, formatting.

Role: the system of record for behavior.

BM25 is often misspelled as BH25; the correct name is BM25. Qwen3 is used only as an embedding model here. Phi-4 is the language-and-routing layer. None replaces the others: together they cover literal matching, conceptual matching, conversational intent, and deterministic execution.

Why hybrid retrieval

Exact words and human meaning fail in opposite directions.

BM25 sees the text

  • “Chase Visa” → strong exact match
  • “142.50” → structured exact match
  • “power bill” → may miss “PSE Electricity”
PLUS

Qwen3 sees the meaning

  • “power bill” → PSE Electricity
  • “home internet” → Xfinity Broadband
  • Exact unseen amounts → dangerous approximation

Reciprocal Rank Fusion combines ranks—not incomparable BM25 and cosine scores.

The hybrid design avoids choosing one retrieval ideology. Lexical retrieval is precise but vocabulary-sensitive. Embeddings understand paraphrases but can confidently return the nearest wrong record. Reciprocal Rank Fusion rewards agreement and strong rank positions without pretending the raw scores share a scale.

Pitfall 1

“OpenAI-compatible” did not mean identical tool behavior.

What failed

Phi-4 Mini sometimes emitted tool requests as ordinary JSON text instead of structured tool_calls. The standard agent loop treated that text as the final answer.

How it was fixed

The local adapter recognizes native calls and JSON-text calls. Python intent coverage restores required read-only tools when metadata is absent.

Compatibility is a protocol claim—not a reliability guarantee.

The lesson is to inspect raw provider responses before trusting a framework abstraction. Tool schemas can be accepted while the response semantics differ. The fallback is safe only because these tools are read-only. The same fallback must not be copied to tools that send email, transfer money, or modify records.

Pitfall 2

A correct tool result can still become incorrect prose.

Correct JSONTrusted dates and totals
→
Model rewriteInvented dates, changed periods, confused amounts
→
Python formatterStable, typed, factual presentation

Fix

Phi-4 selects intent; deterministic code formats all financial results. Model prose is allowed only where variation cannot alter the truth.

Many agent designs stop validating once a tool returns good data. This project found the second failure boundary: synthesis. A model can distort authoritative data while making it sound more natural. Deterministic formatting eliminates that risk for financial output.

Pitfall 3

Token search broke a decimal amount into false evidence.

Observed

Query: 142.40 Tokens: "142" OR "40" Result: unrelated partial matches

Fixed

Detect money/date patterns → compare structured fields exactly → no exact match means no result

In financial retrieval, “nearest” is not a substitute for “equal.”

SQLite FTS5 did exactly what a text engine should do: tokenize punctuation. But that behavior is wrong for money. The fix detects two-decimal amounts and ISO dates before full-text tokenization, validates them against structured fields, and prevents semantic fallback from approximating an unmatched exact value.

Pitfall 4

Cross-tool joins leaked unrelated bills.

Before

Search ranked PSE Electricity first, but the due-date tool returned Chase, PSE, and Citi. The answer ignored the user’s phrase “only for rank 1.”

After

Retrieval rank 1 supplies a stable bill_id. Due and change details join only on that ID. No search match suppresses unrelated details.

Agent tools do not compose safely by accident; joins are application logic.

This is a classic data-system problem appearing inside an agent. The model’s prose and list position are not keys. Stable identifiers are. The same rule applies to document assistants, support systems, medical records, and enterprise copilots: retrieve an entity ID, then use that ID for downstream actions or enrichment.

General learning

A reusable pattern for trustworthy AI systems.

1. Establish truth

Build and test deterministic behavior before adding a model.

2. Separate roles

Let models interpret; let code enforce rules and state.

3. Retrieve twice

Combine lexical precision with semantic recall.

4. Fail closed

Exact values, missing matches, and write actions require certainty.

5. Join by ID

Never connect tools through generated prose or display names.

6. Test boundaries

Provider response, routing, retrieval, joins, synthesis, and output.

These six ideas are the transferable product. They apply beyond bills: customer support, compliance, operations, healthcare, education, or any assistant using enterprise data. The architecture is less about picking the best model and more about defining where probabilistic behavior is acceptable.

What a systems-minded reviewer would ask next

Can it prove value beyond a six-record demonstration?

Evidence

  • Build a representative email and statement dataset
  • Track Recall@3 and Mean Reciprocal Rank
  • Measure exact-match false positives
  • Record latency and local resource cost

Trust

  • Attach source IDs and citations to every answer
  • Separate ingestion from normalized bill records
  • Monitor model and runtime version changes
  • Require confirmation before any future write tool
A strong technology review should challenge the demo with measurement. Does hybrid retrieval outperform each component on real data? What are the failure categories? What does local inference cost in time and memory? Can every answer point back to a source? These questions convert an experiment into an engineering system.

Gate for every stage

No new autonomy until the previous stage is measurable, observable, and safe under failure.

The immediate gap is that retrieval searches synthetic normalized records, not real emails. Read-only Gmail ingestion should come before any action capability. The output should preserve source references. Only after retrieval quality and failure behavior are measured should the project consider reminders or writes—and those require explicit confirmation.

Closing idea

The breakthrough is not that the model can answer.
It is that the system knows what the model must not decide.

A small local model becomes useful when surrounded by retrieval, deterministic tools, stable identifiers, validation, and evidence.
